## 3. Requirements and Traceability

The requirements for GenAI Practitioner v2 were derived from the problem context established in Section 2: a Bournemouth, Christchurch and Poole resident with low- or medium-acuity symptoms needs a calm, local, safety-bounded way to decide between self-care, pharmacy, GP, NHS 111, urgent treatment, or emergency care. The requirements therefore focus less on building a general medical chatbot and more on producing a defensible care-navigation prototype. This distinction matters because the system handles health-related input, but it is not clinically commissioned, clinically validated, or intended to diagnose. The requirements prioritise local signposting, conservative escalation, transparent reasoning, and resilience when external services or the optional LLM are unavailable.

| ID | Requirement | Rationale | Prototype traceability |
| --- | --- | --- | --- |
| R1 | The system must support symptom-led triage using low, medium, and high urgency categories. | Users need differentiated next steps, not a generic answer. | `AITriageRequest`, `UrgencyLevel`, and deterministic scoring in `backend/services/shared/triage_logic.py`. |
| R2 | Emergency warning signs must trigger immediate escalation advice. | Under-escalation is the highest safeguarding risk. | Emergency override, high-risk keyword matching, and `999` guidance in `triage_logic.py`. |
| R3 | The system must provide Bournemouth-relevant service signposting. | The brief requires a local Bournemouth-focused community service tool. | Curated service cards in `knowledge_base.py` and local facilities in `facility_catalog.py`. |
| R4 | The system must retrieve supporting guidance rather than relying only on generative output. | Retrieval improves transparency and limits hallucination risk. | Knowledge service `/retrieve`, lexical scoring, urgency hints, and surfaced knowledge cards. |
| R5 | The system should recommend nearby care options according to urgency and optional location. | Advice becomes more useful when it is connected to practical local access. | Facility recommendation service, route metrics, suitability score, and mobile facility cards. |
| R6 | The system should support transport guidance for ambulance, ride-hailing, or self travel. | Urgent-care navigation includes how the user safely reaches care. | `transport/main.py` ranks transport modes using urgency, mobility, ambulance delay, and emergency flags. |
| R7 | The LLM must not control the core triage decision. | A safety-critical decision should be inspectable, deterministic, and testable. | Optional LLM refinement in `medical_llm.py` is instructed not to change urgency or invent diagnoses. |
| R8 | The prototype must continue functioning without the optional LLM. | A demo and future deployment should not fail if an API key, provider, or model is unavailable. | `MEDICAL_LLM_ENABLED` gate and `rules+rag` fallback label. |
| R9 | The mobile interface must collect only the data needed for safer guidance. | This supports privacy, usability under stress, and data minimisation. | Symptoms, known conditions, age, duration, pain, mobility, emergency flag, and optional location in `App.tsx`. |
| R10 | The system must show enough reasoning for a user or marker to understand the recommendation. | Transparency reduces blind trust and supports evaluation. | `reasoning`, `recommended_actions`, `knowledge_cards`, `decision_trace`, and visible safety disclaimer. |

The traceability table shows that the prototype is organised around the assessed problem rather than around technical novelty alone. For example, R7 and R8 directly shaped the most important architectural decision: the LLM is positioned as a wording and follow-up assistant rather than as the triage authority. Similarly, R3, R4, and R5 explain why the system contains a local knowledge base and facility catalogue instead of returning a single free-text answer. The mobile interface also reflects the requirements: the user journey begins with symptom and risk capture, then moves to urgency, reasoning, actions, transport, nearby care, retrieval evidence, and bounded follow-up. This creates an end-to-end workflow that can be demonstrated at prototype level while remaining honest about clinical limits.

## 4. Design Rationale and Technical Approach

GenAI Practitioner v2 uses an Expo React Native mobile client and a FastAPI backend arranged as a small microservice-style system. The mobile app acts as the user-facing triage surface: it collects symptom text, contextual risk details, optional location, mobility status, and whether emergency signs are already confirmed. These fields are sent to a gateway service, which provides one stable API boundary for the app. Behind that gateway, separate services handle triage, knowledge retrieval, facility recommendation, transport recommendation, and follow-up chat. This architecture is more complex than a single endpoint, but it is justified because each part of the system carries a different responsibility and risk profile.

The central design choice is that the system is rules-first, retrieval-second, and LLM-third. The triage service first runs deterministic logic over the submitted symptoms and risk factors. High-risk terms such as chest pain, severe breathlessness, stroke-like symptoms, collapse, seizure, or bleeding can immediately raise urgency. Medium-risk symptoms such as fever, infection, vomiting, diarrhoea, rash, urinary symptoms, migraine, ear pain, persistent cough, and sore throat raise caution without automatically creating an emergency route. Age, severe pain, long duration, and long-term conditions such as asthma, diabetes, COPD, pregnancy, heart disease, immunocompromise, and stroke history add further safeguards. This deterministic layer is deliberately conservative and inspectable: it produces an urgency category, a summary, reasoning statements, recommended actions, self-care advice when appropriate, over-the-counter suggestions when appropriate, a search query for retrieval, and a decision trace.

After the rules layer assigns urgency, the triage service calls the knowledge service. The current RAG approach is lightweight retrieval-augmented generation, not an embedding-based vector database. The knowledge base is a curated set of local and NHS-style knowledge documents stored in `backend/services/shared/knowledge_base.py`. Each document has an id, title, source, category, tags, body text, and urgency hint. Retrieval tokenises the user's generated search query and each document using a simple regular expression, scores overlap between query tokens and document content, adds a small boost when the document urgency hint matches the triage urgency, and adds a smaller service-document boost. The top cards are returned to the app as structured `KnowledgeCard` objects with title, source, snippet, category, and relevance score.

This RAG design is intentionally modest. Its strength is that it is transparent, auditable, and easy to align with local Bournemouth signposting. A reviewer can inspect every knowledge card and see exactly why the app might surface NHS 111, Bournemouth Urgent Treatment Centre, Royal Bournemouth Hospital A&E, Poole Hospital A&E, pharmacy support, transport guidance, or safeguarding guidance for older adults and complex conditions. The limitation is that it does not provide the semantic recall of a vector database and may miss unusual wording. For this prototype, that trade-off is acceptable because the retrieval layer supports signposting and explanation; it does not replace clinical judgement or the red-flag scoring layer.

The facility and transport services make the output actionable. Facility recommendations are selected from a Bournemouth and nearby Dorset catalogue containing hospitals, urgent care, GPs, and pharmacies. The ranking changes by urgency: high urgency favours hospital and urgent care, medium urgency favours urgent care and GP options, and low urgency favours pharmacy and GP support. If the user shares location, route assessment uses OSRM road routing where available and falls back to a local distance heuristic if the external route request fails. The returned route metrics include distance, travel minutes, average speed, traffic level, and source. Transport recommendation is then ranked separately using urgency, mobility limitation, emergency flag, and optional ambulance delay. This separation is useful because the closest facility is not always the safest transport mode.

The LLM layer is intentionally constrained. The current optional model configuration uses `S4nfs/Neeto-1.0-8b` through an OpenAI-compatible Hugging Face Router endpoint, with the `:fastest` routing suffix used for low-latency prototype inference. The model is an 8B Llama-architecture text-generation model tagged as medical, biomedical, conversational, and fine-tuned on medical question-answering datasets. It was chosen for practical prototype reasons: it is small enough for responsive hosted inference, compatible with the existing OpenAI client interface, and relevant to medical wording tasks. However, the report should not claim that this model is clinically validated or safe to make triage decisions. The app's safety argument is the opposite: the model is optional and cannot set the urgency category.

In `medical_llm.py`, the triage refinement prompt instructs the model not to change urgency, not to invent diagnoses, not to invent facilities, not to invent transport advice, and not to invent medicines. It can only rewrite the existing structured output for clarity, brevity, and patient-friendly wording. It must return JSON with expected keys. If the model fails, returns invalid JSON, or is not configured, the backend returns the deterministic `rules+rag` response. The follow-up chat prompt is also bounded: it tells the model not to diagnose, to use only supplied knowledge snippets, to keep answers short, and to include emergency escalation if symptoms sound severe. This makes the model a communication layer, not a clinical authority.

The gateway supports this design by hiding service complexity from the mobile app. The app sends `/ai-triage`, `/chat`, `/knowledge`, or `/nearest-hospital` requests to one backend entry point. The gateway proxies requests to the appropriate internal service and exposes a `/health` endpoint that checks whether the triage, knowledge, facility, and chat services are available. Inside the triage service, dependency failures are also handled pragmatically: if the knowledge service, facility service, or transport service cannot be reached, local fallback functions are used. This matters because a prototype assessed in a live demonstration should not depend entirely on every service and external provider being available at the exact same time.

The mobile interface completes the architecture by presenting the result as a care-navigation flow rather than a chatbot answer. The user first enters symptoms and basic risk details, then chooses safety and location toggles. The result screen separates urgency, reasoning, recommended actions, transport, nearby care, retrieval evidence, urgent questions, and safety disclaimer. This layout supports the ethical goal of avoiding over-reliance: the user can see why the app made a recommendation, which local services were surfaced, what action is suggested, and where the system's limits are. For a coursework prototype, the architecture therefore demonstrates a feasible and professionally defensible pattern: deterministic triage for safety, curated RAG for local relevance, route-aware service ranking for actionability, and tightly bounded LLM use for patient-friendly communication.
