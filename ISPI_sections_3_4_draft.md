## 3. Requirements and Traceability

The requirements for GenAI Practitioner v2 were derived from the problem context established in Section 2: a Bournemouth, Christchurch and Poole resident with low- or medium-acuity symptoms needs a calm, local, safety-bounded way to decide between self-care, pharmacy, GP, NHS 111, urgent treatment, or emergency care. The requirements therefore focus less on building a general medical chatbot and more on producing a defensible care-navigation prototype. This distinction matters because the system handles health-related input, but it is not clinically commissioned, clinically validated, or intended to diagnose. The requirements prioritise LLM-led symptom triage, local signposting, conservative safety constraints, transparent reasoning, and resilience when external services fail.

| ID | Requirement | Rationale | Prototype traceability |
| --- | --- | --- | --- |
| R1 | The system must use an LLM for the core symptom-led triage decision across low, medium, and high urgency categories. | The project brief and implementation goal require generative clinical reasoning rather than a purely deterministic symptom scorer. | `generate_triage_assessment()` in `backend/services/shared/medical_llm.py` returns urgency, reasoning, actions, self-care advice, OTC options, and a search query. |
| R2 | Deterministic rules must act as safety guardrails, not as the normal triage engine. | Rules are still necessary to prevent dangerous under-escalation, but should restrict unsafe LLM output rather than replace the LLM. | `assess_safety_constraints()` calculates minimum safe urgency, and `apply_safety_constraints()` raises unsafe LLM outputs when red flags are present. |
| R3 | Emergency warning signs must trigger immediate escalation advice. | Under-escalation is the highest safeguarding risk in a health-navigation tool. | Emergency override, high-risk keyword matching, high-urgency minimums, and `999` guidance in `triage_logic.py`. |
| R4 | The system must provide Bournemouth-relevant service signposting. | The brief requires a local Bournemouth-focused community service tool, not generic medical text. | Curated service cards in `knowledge_base.py` and local facilities in `facility_catalog.py`. |
| R5 | The system must retrieve supporting guidance rather than relying only on generative output. | Retrieval improves transparency, local grounding, and hallucination resistance. | Knowledge service `/retrieve`, lexical scoring, urgency hints, and surfaced knowledge cards. |
| R6 | The system should recommend nearby care options according to urgency and optional location. | Advice becomes more useful when it is connected to practical local access. | Facility recommendation service, route metrics, suitability score, and mobile facility cards. |
| R7 | The system should support transport guidance for ambulance, ride-hailing, or self travel. | Urgent-care navigation includes how the user safely reaches care. | `transport/main.py` ranks transport modes using urgency, mobility, ambulance delay, and emergency flags. |
| R8 | The prototype must degrade safely if the LLM is unavailable. | A demo should not crash if an API key, provider, or model is unavailable, but fallback must not pretend to be full clinical triage. | `MEDICAL_LLM_ENABLED` gate, `safety-guardrails` model label, and conservative fallback guidance in `build_safety_fallback_assessment()`. |
| R9 | The mobile interface must collect only the data needed for safer guidance. | This supports privacy, usability under stress, and data minimisation. | Symptoms, known conditions, age, duration, pain, mobility, emergency flag, and optional location in `App.tsx`. |

The traceability table shows that the prototype is organised around the assessed problem rather than around technical novelty alone. R1 and R2 are the most important corrections from the earlier version: the LLM now owns the clinical triage decision, while deterministic logic only restricts the model from giving unsafe or under-escalated advice. R4, R5, and R6 explain why the system contains a local knowledge base and facility catalogue instead of returning a single free-text answer. The mobile interface also reflects the requirements: the user journey begins with symptom and risk capture, then moves to urgency, reasoning, actions, transport, nearby care, retrieval evidence, and bounded follow-up. This creates an end-to-end workflow that can be demonstrated at prototype level while remaining honest about clinical limits.

## 4. Design Rationale and Technical Approach

GenAI Practitioner v2 uses an Expo React Native mobile client and a FastAPI backend arranged as a small microservice-style system. The mobile app acts as the user-facing triage surface: it collects symptom text, contextual risk details, optional location, mobility status, and whether emergency signs are already confirmed. These fields are sent to a gateway service, which provides one stable API boundary for the app. Behind that gateway, separate services handle triage, knowledge retrieval, facility recommendation, transport recommendation, and follow-up chat. This architecture is more complex than a single endpoint, but it is justified because each part of the system carries a different responsibility and risk profile.

The central design choice is now LLM-first, retrieval-supported, and guardrail-bounded. The triage service first runs a narrow safety pass over the submitted request. This pass is not intended to diagnose or to complete the normal triage decision. Its role is to identify emergency warning signs, severe pain, age-related risk, mobility limitations, and high-risk long-term conditions that the LLM must not ignore. The result is a `SafetyAssessment` containing a minimum allowed urgency, red flags, caution flags, a retrieval query, and a decision trace. For example, chest pain or severe breathlessness forces a high-urgency minimum, while severe pain, very young or older age, and conditions such as asthma, COPD, diabetes, pregnancy, stroke history, heart disease, or immunocompromise can force at least medium urgency. These constraints are a safety boundary around the model, not the main reasoning pathway.

The system then performs retrieval before the LLM call. The current RAG approach is lightweight retrieval-augmented generation, not an embedding-based vector database. The knowledge base is a curated set of local and NHS-style knowledge documents stored in `backend/services/shared/knowledge_base.py`. Each document has an id, title, source, category, tags, body text, and urgency hint. Retrieval tokenises the guardrail-generated query and each document using a simple regular expression, scores overlap between query tokens and document content, adds a small boost when the document urgency hint matches the safety context, and adds a smaller service-document boost. The top cards are passed into the LLM prompt and later surfaced to the app as structured `KnowledgeCard` objects with title, source, snippet, category, and relevance score.

This RAG design is intentionally modest. Its strength is that it is transparent, auditable, and easy to align with local Bournemouth signposting. A reviewer can inspect every knowledge card and see exactly why the app might surface NHS 111, Bournemouth Urgent Treatment Centre, Royal Bournemouth Hospital A&E, Poole Hospital A&E, pharmacy support, transport guidance, or safeguarding guidance for older adults and complex conditions. The limitation is that it does not provide the semantic recall of a vector database and may miss unusual wording. For this prototype, that trade-off is acceptable because the retrieval layer supports signposting and context, while the LLM performs the symptom-led reasoning and the guardrails prevent unsafe under-escalation.

The LLM layer is therefore the core triage layer, not an optional wording layer. In `medical_llm.py`, `generate_triage_assessment()` sends the patient input, retrieved local knowledge cards, and safety guardrails to an OpenAI-compatible chat-completion endpoint. The prompt instructs the model to choose exactly one urgency category: low, medium, or high. It must return JSON containing the urgency, summary, reasoning, recommended actions, self-care advice, OTC options, and search query. The same prompt also restricts risky behaviour: the model must not choose below the guardrail minimum, must not invent facilities, service hours, phone numbers, medicines, or diagnoses, must not prescribe treatment, and must escalate when symptoms are severe, sudden, worsening, or uncertain.

The selected default triage model is `m42-health/Llama3-Med42-8B` through Hugging Face Router's `featherless-ai` text-generation provider. It was chosen because it is a healthcare and clinical LLM intended for medical-style conversational reasoning, making it more appropriate for the symptom-triage layer than a general chat model. Runtime checks showed that it is not exposed through the generic chat-completions route on the current account, so the implementation calls it through the completions interface using a Llama 3 prompt template. Follow-up chat is deliberately separated and uses `Qwen/Qwen2.5-72B-Instruct:fastest`, a chat-capable model, because conversational clarification has a different risk profile from first-pass triage. This is not a claim of clinical validation: the safety case still depends on guardrails, structured JSON validation, RAG grounding, visible disclaimers, and scenario testing.

After the model returns JSON, the backend validates and normalises the output. If the model returns invalid JSON, omits urgency, or is unavailable, the triage service does not silently continue as if full triage succeeded. It falls back to `build_safety_fallback_assessment()`, labels the response as `safety-guardrails`, and gives conservative safety signposting. If the LLM does respond, `apply_safety_constraints()` post-processes the result. This function raises urgency if the LLM selected below the minimum safe level, inserts emergency reasoning and `999` guidance where needed, removes self-care and OTC suggestions from high-urgency responses, and ensures medium-urgency outputs include same-day or NHS 111 style escalation. This is the key implementation of the user's intended architecture: the LLM reasons about triage, while deterministic code prevents dangerous answers.

The facility and transport services make the output actionable. Facility recommendations are selected from a Bournemouth and nearby Dorset catalogue containing hospitals, urgent care, GPs, and pharmacies. The ranking changes by final guarded urgency: high urgency favours hospital and urgent care, medium urgency favours urgent care and GP options, and low urgency favours pharmacy and GP support. If the user shares location, route assessment uses OSRM road routing where available and falls back to a local distance heuristic if the external route request fails. The returned route metrics include distance, travel minutes, average speed, traffic level, and source. Transport recommendation is then ranked separately using urgency, mobility limitation, emergency flag, and optional ambulance delay. This separation is useful because the closest facility is not always the safest transport mode.

The gateway supports this design by hiding service complexity from the mobile app. The app sends `/ai-triage`, `/chat`, `/knowledge`, or `/nearest-hospital` requests to one backend entry point. The gateway proxies requests to the appropriate internal service and exposes a `/health` endpoint that checks whether the triage, knowledge, facility, and chat services are available. Inside the triage service, dependency failures are also handled pragmatically: if the knowledge service, facility service, or transport service cannot be reached, local fallback functions are used. This matters because a prototype assessed in a live demonstration should not depend entirely on every service and external provider being available at the exact same time.

The mobile interface completes the architecture by presenting the result as a care-navigation flow rather than a chatbot answer. The user first enters symptoms and basic risk details, then chooses safety and location toggles. The result screen separates urgency, reasoning, recommended actions, transport, nearby care, retrieval evidence, urgent questions, and safety disclaimer. This layout supports the ethical goal of avoiding over-reliance: the user can see why the app made a recommendation, which local services were surfaced, what action is suggested, and where the system's limits are. For a coursework prototype, the architecture therefore demonstrates a feasible and professionally defensible pattern: LLM-led clinical triage, curated RAG for local relevance, deterministic safety guardrails, route-aware service ranking, and bounded follow-up.
